# 豆包网页登录接入说明

## 设计边界

`doubao-web` 使用豆包网页账号的登录状态，不读取豆包桌面端目录，也不要求火山方舟 API Key。
登录过程由 `dsh-web-providers login doubao` 启动一个独立 Chrome 上下文，用户完成登录后，
插件只保存 `doubao.com` 的 Cookie、Local Storage 和网页请求所需设备参数。

凭据以单个 JSON 字符串保存到 DSH 凭据引用 `DOUBAO_WEB_LOGIN_SESSION`。CLI 使用临时文件
原子替换 `.credentials.yaml`，并强制文件权限为 `0600`。任何 Cookie 或账号标识都不能进入
日志、Git 仓库或 `settings.yaml`。

## 请求流程

1. DSH 将系统提示词、完整消息记录和工具 JSON Schema 交给 `doubao-provider.js`。
2. Provider 把上下文编码为一条豆包网页消息，不复用豆包服务端历史。
3. `doubao-browser.js` 以保存的 Storage State 启动无界面 Chrome，并加载豆包聊天页。
4. 请求在网页上下文中调用 `/chat/completion`。官网脚本自行添加当前 `msToken` 和
   `a_bogus`，插件不实现或保存签名算法。
5. 浏览器把 SSE 字节流逐块回传给 pi-ai 的 `AssistantMessageEventStream`。
6. DSH 收到文本、思考内容或工具调用，并继续自己的 Agent 循环。

当前网页协议使用 `client_meta`、`messages`、`option`、`user_context` 和 `ext` 五个顶层字段。
返回流以首个 `content` 包和后续 `patch_op` 增量组成，`end_type: 3` 表示本轮结束。旧版
`event_type/event_data` 流仍保留兼容解析，便于豆包灰度回滚时继续工作。

## 工具调用

豆包消费端协议没有 OpenAI 风格的原生 `tool_calls`。Provider 在存在 DSH 工具时加入严格的
XML 边界和 JSON 信封约定：

```text
<dsh_tool_calls>{"tool_calls":[{"name":"tool_name","arguments":{}}]}</dsh_tool_calls>
```

只有当整个回复完全匹配信封、工具名存在于本轮 DSH 工具目录、且参数是 JSON 对象时，回复
才会转换为 `toolCall`。其他 JSON 或相似文本一律作为普通回答，避免误执行未知工具。

## 兼容与维护

豆包消费端网页协议不是公开 API，字段和端点可能变化。维护时优先抓取当前网页自身发出的
请求并更新适配层，不要把逆向的 `a_bogus` 实现复制进仓库。真实集成测试至少验证：

- 网页登录后能够保存和重新加载凭据；
- 普通模式可以流式返回指定短文本；
- 深度思考模式能够完成回复；
- 工具指令被转换为合法 DSH `toolCall`；
- 凭据值和账号标识没有出现在测试输出或 Git diff 中。
